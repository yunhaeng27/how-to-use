# 매뉴얼 시나리오 테스트

이 스킬은 이 저장소(온보딩 매뉴얼)가 실제로 "처음 보는 사람"에게 통하는지를, 그 사람인 척 연기시키는 게 아니라 **진짜로 그 상황에 놓인 서브에이전트**를 통해 검증한다. 서브에이전트("테스터")에게는 시나리오의 역할과 목적만 전달하고, 이것이 테스트라는 사실은 절대 알리지 않는다. 그래야 테스터가 매뉴얼을 진짜 필요에 의해 읽고, 진짜로 헷갈리고, 진짜로 판단을 내린다 — 그 반응이 곧 매뉴얼의 품질 신호다. 결론에 매끄럽게 도달했는지 못지않게, 그 과정에서 테스터가 실제로 겪는 망설임·재탐색·막힘의 순간 자체가 매뉴얼 품질 신호라는 점을 잊지 않는다 — 예를 들어 문서가 안내한 예제 링크를 따라갔는데 그 디렉토리에 설명이 전혀 없어 막막해지는 순간도 놓치지 않고 잡아내야 한다.

동시에 테스터는 실제 도구 접근 권한을 가진 에이전트이므로, 오케스트레이터(스킬을 실행하는 나)는 테스터가 실제 GenOS·외부 시스템·원격 저장소에 영향을 줄 행동을 시도하는 순간 이를 감지하고 중단시켜야 한다. **몰입감 유지(테스트임을 숨김)와 안전 개입(위험 행동 차단)은 둘 다 타협 불가능한 요구사항이다.**

## 입력

사용자가 시나리오를 자연어로 준다. 예:

> "너는 genon 신입사원 개발자임. genos 개발하려는데 langfuse에 대해 전혀 몰라서 온보딩을 하려다 해당 매뉴얼을 발견함. genos에서 langfuse를 사용하려면 어떻게해야하는지 알고 싶음"

이 입력에는 두 종류의 텍스트가 섞여 있을 수 있다:

1. **메타 지시문** — "이런식으로 시나리오가 주어지면", "테스트한다", "평가한다" 등. 이건 나(오케스트레이터)를 위한 지시일 뿐, 테스터에게 절대 전달하지 않는다.
2. **시나리오 본문(역할+목적)** — 테스터에게 그대로, 혹은 자연스러운 1인칭 상황문으로 다듬어서 전달할 부분.

시나리오가 여러 개 연속으로 주어질 수도 있다. 각 시나리오는 독립된 테스터 1명 + 리포트 1개로 처리한다.

## 절차

### 1. 시나리오 정제

입력에서 역할과 목적만 추출한다. "시나리오", "테스트", "평가", "리포트", "모니터링", "서브에이전트" 같은 메타 단어가 하나라도 테스터 프롬프트에 섞여 들어가지 않았는지 반드시 다시 확인한다. 정제된 결과는 1인칭 상황 설명문 형태로 만든다 — 예: "당신은 genon의 신입 개발자입니다. GenOS를 개발하려는데 Langfuse를 전혀 모릅니다. 온보딩 중 이 저장소(매뉴얼)를 발견했습니다. GenOS에서 Langfuse를 어떻게 써야 하는지 알아내고 싶습니다."

### 2. 안전 준비 (테스터 실행 전에 반드시 완료)

- `test/` 디렉토리가 없으면 만든다(리포트 저장용).
- 테스터는 **`isolation: "worktree"`** 로 실행한다 — 실제 `main` 브랜치·원격 저장소와 분리된 워크트리에서 동작하게 해, 테스터가 무슨 파일을 만들거나 커밋을 하더라도 실제 저장소는 건드리지 않는다.
- 테스터에게 실제 GenOS 접속 정보, 사내 URL, API 토큰, 자격증명을 **절대 지어내어 제공하지 않는다.** 이건 회피가 아니라 사실 그대로다 — 신입사원은 실제로 그런 걸 아직 갖고 있지 않다. 테스터가 "로그인해서 실제로 등록해보자"는 판단을 내리더라도, 실제 자격증명이 없으니 시도는 곧바로 막힌다. 이 부재 자체가 1차 안전장치다.
- 테스터에게 별도의 위험한 실행 권한(실제 배포 스크립트, 실제 서비스 계정)을 주지 않는다 — 주어진 저장소와 일반 개발 도구 외에는 아무것도 쥐어주지 않는다.

### 3. 테스터 생성

`Agent` 도구로 실행한다.

- `subagent_type`: `"general-purpose"` (신입 개발자가 실제로 할 만한 탐색·실습·판단을 자연스럽게 재현하려면 범용 에이전트가 맞다. `fork`는 쓰지 않는다 — fork는 지금까지의 대화 맥락(이게 테스트라는 사실 포함)을 그대로 물려받기 때문에 몰입이 깨진다).
- `isolation`: `"worktree"`.
- `prompt`: 1단계에서 정제한 상황문 + 다음 두 가지를 자연스러운 문장으로 덧붙인다.
  1. "지금 당신이 있는 이 디렉토리가 그 매뉴얼 저장소입니다. 필요한 걸 직접 찾아보고, 필요하면 예제도 실행해보고, 목적을 달성해 보세요."
  2. "아직 코드베이스에 익숙하지 않으니 가능하면 문서만 보고 해결하고 싶고, 소스 코드를 직접 파고드는 건 최후의 수단으로 남겨두고 싶습니다. 진행하면서 든 생각·판단·헷갈렸던 부분은 가감 없이 그때그때 적어가며 진행하세요."
  두 번째 문장은 실제 신입사원이라면 자연스레 갖는 태도이지 테스트를 암시하는 표현이 아니다 — 그럼에도 "시나리오", "테스트", "평가", "리포트", "모니터링" 같은 메타 단어는 절대 섞이지 않아야 한다. 이 두 문장 외에 추가 설명·배경·주의사항을 덧붙이지 않는다 — 주면 몰입이 깨지거나 실제 신입사원이 받지 않을 힌트를 주는 셈이다.
- 이름은 시나리오를 요약한 slug로 준다(예: `newbie-langfuse-onboarding`).

### 4. 지속 모니터링 — 위험 행동 감지 시 즉시 중단

테스터가 실행되는 동안, 다음 신호가 보이면 **즉시 `TaskStop`으로 중단**한다. 판단을 미루거나 "일단 끝까지 지켜본다"는 선택은 없다 — 신호가 보이는 즉시 멈춘다.

중단 대상 신호:
- 원격 저장소에 영향을 주는 행동: `git push`, PR/이슈 생성, 원격 브랜치 생성, `main`에 대한 어떤 조작.
- 실제 외부/내부 시스템에 대한 네트워크 요청: 진짜 GenOS 내부 URL, 진짜 Langfuse 클라우드 프로젝트, 그 외 이 매뉴얼 저장소 바깥의 실서비스에 자격증명·토큰을 실어 보내는 요청. (예제 코드를 로컬에서 실행하다 `.env` placeholder 값으로 실패하는 것은 정상이며 중단 대상이 아니다 — 실제 값을 알아내거나 지어내 실제 서비스에 도달하려는 시도만 막는다.)
- 파괴적 명령: `rm -rf`, force-push, 대량 삭제, 시스템 설정 변경.
- 브라우저 자동화 도구로 실제 로그인 페이지·실제 콘솔에 값을 입력하거나 제출하는 행동.

모니터링 방법:
- Agent 실행이 백그라운드 태스크로 전환되면 완료 시 도착하는 task-notification을 기다리되, 그 사이 `TaskOutput`(`block: false`)으로 중간 상태를 주기적으로 확인할 수 있으면 확인한다.
- 위 신호 중 하나라도 발견되면: `TaskStop` 호출 → 그 시점까지 테스터가 한 행동과 중단 시점·사유를 그대로 기록해 둔다(리포트에 반드시 남긴다).
- 위험 신호 없이 테스터가 스스로 마무리하면 정상 종료로 처리한다.

### 5. 결과 수집

테스터의 최종 응답과, 테스터가 어떤 문서를 언제 읽었는지·어떤 순서로 판단했는지·어디서 멈추거나 되돌아갔는지를 가능한 범위에서 재구성한다. 정상 종료든 강제 중단이든 이 단계는 항상 수행한다.

이때 테스터가 도달한 **핵심 결론 하나하나에 대해, 그 근거가 매뉴얼 산문 문서였는지 아니면 코드를 직접 읽고 분석·재구성한 것이었는지를 구분**한다. 실제 사람은 매뉴얼을 읽고 이해한 다음, 실제 GenOS 코드 서빙에 올려서 동작을 확인하는 흐름으로 움직인다 — 코드를 정독해서 동작을 역추적하는 데는 시간이 오래 걸리고, 실제 사람이 그렇게까지 하리라는 보장이 없다. 따라서:

- 어떤 결론에 **문서만으로 도달**했다면, 그 문서가 제 역할을 한 것이다.
- 어떤 결론이 **코드를 읽고 분석해야만 나왔다면**, 그건 매뉴얼이 그 내용을 산문으로 설명하지 못했다는 신호다 — "문서만으로는 이해가 불가능했던 지점"으로 표시하고, 정확히 어느 코드 파일의 어떤 부분에서 그 정보를 얻었는지 남긴다.

추가로, 테스터의 행동·판단 기록에서 아래와 같은 **막힘 포인트(stuck moment)** 신호를 놓치지 않고 잡아낸다 — 최종적으로 결론에 도달했는지와 무관하게, 그 순간 자체가 매뉴얼 품질 신호다:

- 문서가 안내한 링크·경로·예제 디렉토리를 따라갔지만 설명(README 등)이 없어 다음 행동을 스스로 추측해야 했던 경우.
- 문서가 언급한 파일·명령·설정값이 실제 저장소 상태와 다르거나 존재하지 않는 경우.
- 실행 순서나 선행 조건이 명시되어 있지 않아 순서를 추측하거나 같은 문서/디렉토리로 여러 번 되돌아간 경우.
- 실행 중 에러가 났는데 문서에 대응 안내가 없어 스스로 원인을 찾아야 했던 경우.
- 서로 다른 문서 간 내용이 어긋나거나 모순되어 어느 쪽을 믿어야 할지 판단이 필요했던 경우.
- 다음에 뭘 해야 할지 안내가 없어 여러 문서를 오가며 헤맨 경우.

테스터가 "막막하다"고 명시적으로 쓰지 않아도, 망설임·재탐색·경로 되돌아가기·같은 문서 재독 같은 행동 패턴에서 이런 순간을 유추해 잡아낸다. 발견한 막힘 포인트마다 정확한 위치(파일 경로·디렉토리·문서 섹션)를 남긴다.

### 6. 평가 및 개선 리포트 작성 → `test/` 폴더

파일명: `test/<YYYYMMDD>_<시나리오-슬러그>.md` (오늘 날짜 기준, 예: `test/20260917_newbie-langfuse-onboarding.md`).

리포트 구성:

1. **시나리오 원문** — 사용자가 준 그대로.
2. **테스터 행동 흐름도** — mermaid `flowchart`로, 시간순: 어떤 문서/파일을 열었는지 → 거기서 어떤 판단·오해를 했는지 → 다음에 뭘 했는지(다른 문서로 이동/예제 실행/포기/결론 도출) → 최종 결과. 강제 중단이 있었다면 그 지점을 흐름도에 명시. **막힘 포인트가 있었다면 해당 노드를 별도 스타일(예: 빨간 계열 색상, 🛑 표시)로 눈에 띄게 표시**한다.
3. **목표 달성 여부** — 테스터가 "GenOS에서 Langfuse를 어떻게 써야 하는지"에 대해 스스로 낸 결론이 실제로 맞는지, 얼마나 걸렸는지, 어디서 막혔는지.
4. **막힘 포인트(스턱 모먼트)** — 5단계에서 감지한 막힘 포인트를 항목별로 표로 정리한다: 위치(파일·디렉토리·문서 섹션) / 기대했던 것 / 실제로 마주친 것 / 테스터의 반응(망설임·재탐색·포기 등 구체적 행동) / 소요 시간·노력 / 최종 해결 방식(스스로 해결·포기·다른 경로로 우회). 막힘 포인트가 하나도 없었다면 "막힘 포인트 없음"이라고 명시한다.
5. **문서 vs 코드 의존도 분석** — 5단계에서 분류한 결과를 표나 목록으로 정리: "결론 X → 근거: 문서 O / 코드 재구성" 형태로 결론별 출처를 나열한다. 코드를 읽고 나서야 알 수 있었던 항목이 많을수록, 그 매뉴얼은 이 시나리오에 대해 아직 "문서만으로 충분"하지 않다는 뜻이라는 점을 리포트에 명시적으로 평가한다.
6. **매뉴얼의 강점** — 테스터가 막힘없이 잘 따라간 부분.
7. **개선점** — 구체적인 파일·섹션을 지목해서, 어떤 표현이 불명확했는지, 어떤 순서가 헷갈렸는지, 어떤 전제(사전 지식)를 매뉴얼이 잘못 가정하고 있었는지. 5단계에서 "코드 재구성"으로 분류된 항목과 4단계의 막힘 포인트 항목은 **반드시** 여기 개선점으로 전환한다 — 어느 문서의 어느 섹션에 어떤 내용을 산문으로(막힘 포인트의 경우 어느 디렉토리에 어떤 README·설명을) 추가해야 그 코드 읽기·막힘이 사라지는지까지 구체적으로 제안한다.
8. **안전 개입 기록** — 위험 행동 감지로 중단시킨 적이 있다면 그 내용을 반드시 남긴다(없으면 "위험 행동 없음"이라고 명시).

### 7. 마무리

리포트 경로를 사용자에게 알린다. `git add`/commit/push은 사용자가 별도로 요청하지 않는 한 하지 않는다 — 리포트를 커밋할지는 사용자 판단이다.

## 하지 말 것

- 테스터에게 이 상황이 테스트/시뮬레이션/평가라는 것을 암시하는 어떤 표현도 쓰지 않는다.
- 테스터에게 실제 자격증명·내부 URL·토큰을 지어내어 제공하지 않는다.
- 위험 신호를 감지한 뒤에도 "일단 지켜보자"며 진행을 허용하지 않는다 — 감지 즉시 중단한다.
- 사용자 승인 없이 원격 저장소에 영향을 주는 행동(push, PR/이슈 생성, 실서비스 호출 등)을 하지 않는다.
- 리포트 작성 과정에서 매뉴얼 원문을 함부로 고치지 않는다 — 발견한 개선점은 리포트에만 기록하고, 실제 수정은 별도 작업(및 별도 확인)으로 다룬다.
- `isolation: "worktree"` 없이 테스터를 실행하지 않는다.
