# 가이드 문서 톤앤매너 교정 + PR 생성

이 스킬은 사용자가 작성한 가이드 문서(초안/수정본)를 이 저장소의 컨벤션에 맞게 교정하고, 필요하면 브랜치를 만들어 PR까지 올려준다.

규칙의 유일한 출처는 [`docs/GUIDE_CONVENTIONS.md`](../../../docs/GUIDE_CONVENTIONS.md)다. 이 스킬 파일은 그 문서의 내용을 요약·복제하지 않는다 — 매번 실행 시점의 문서를 그대로 읽어 적용한다. 그래야 사람이든 AI든 컨벤션 문서를 수정한 순간 스킬 동작도 자동으로 최신 규칙을 따르고, 둘 사이에 차이가 생기지 않는다. 규칙 자체를 바꿔야 할 상황이면 이 스킬이 아니라 그 문서를 고칠 것.

## 입력

사용자가 대상 파일 경로를 지정한다(예: `/guide-doc-style 01_Langfuse/04_langfuse_alerting.md`). 경로를 공백으로 나열하면 여러 문서를 한 번에 대상으로 삼는다.

경로가 없으면 diff 기반으로 대상을 자동 탐색한다:

1. `git status --porcelain`과 `git diff --name-only HEAD`로 워킹트리에 변경(스테이지 여부 무관, untracked 포함)이 있는 파일 목록을 모은다.
2. 그중 최상위 `NN_가이드명/` 디렉토리 하위의 `*.md` 파일만 대상으로 남긴다. `docs/GUIDE_CONVENTIONS.md` 자체를 포함해 그 외 변경 파일(코드, 설정 등)은 제외한다.
3. 남은 대상이 없으면 스킬을 중단하고 "diff에 검토할 가이드 문서가 없다"고 사용자에게 알린다.
4. 대상이 있으면 목록을 보여주고 전부 검토할지, 일부만 검토할지 사용자에게 확인받는다.
5. 확정된 각 문서에 대해 아래 절차(1~4단계)를 순서대로 반복 적용한다.

## 절차

### 1. 컨벤션 로드

`docs/GUIDE_CONVENTIONS.md`를 읽는다. 파일이 없으면 스킬을 중단하고 사용자에게 알린다 — 규칙 문서 없이 임의로 톤을 판단하지 않는다.

### 2. 대상 문서 점검

대상 파일을 읽고, 1단계에서 읽은 `docs/GUIDE_CONVENTIONS.md`의 5번 체크리스트 항목을 위에서부터 하나씩 그대로 대상 문서에 대입해 통과 여부를 판단한다. 각 항목의 구체적 판단 기준(디렉토리 구조, 문서 템플릿, 톤앤매너, 마크다운 세부 규칙 등)은 그 문서의 1~4번 섹션을 그때그때 다시 참조한다 — 판단 기준을 이 스킬 파일에 옮겨 적거나 요약해두지 않는다. 문서 내용이 바뀌면 다음 실행부터 바뀐 기준이 그대로 적용된다.

### 3. 교정 적용

- 내용(사실 관계, 코드, 설명 순서)은 임의로 바꾸지 않는다 — 오직 형식/톤/구조만 컨벤션에 맞춘다.
- 애매한 판단(예: 섹션을 나눠야 하는지, 새 디렉토리가 필요한지)은 먼저 사용자에게 묻는다.
- Edit으로 대상 파일을 직접 고친다. 대상 문서 전체를 새로 쓰지 않고 필요한 부분만 수정한다.
- 새 이미지/코드 자산 위치를 옮겨야 하면 `git mv`로 이동해 히스토리를 보존한다.

### 4. 결과 확인

`git diff`로 변경 사항을 사용자에게 보여주고, 컨벤션 체크리스트 중 무엇을 고쳤는지 짧게 요약한다. 문서를 여러 개 처리한 경우 문서별로 diff와 요약을 나눠 보여준다. 이 단계에서 만족하면 다음 단계로, 아니면 되돌아가 반영한다.

### 5. PR 생성 (요청 시 또는 확인 후)

브랜치 생성, 커밋, 푸시, PR 생성은 원격 저장소에 영향을 주는 행동이므로 진행 전 반드시 사용자에게 확인받는다. 문서가 여러 개면 문서별로 PR을 나눌지 하나로 묶을지도 함께 확인한다.

먼저 현재 브랜치가 이슈에 엮여 있는지 확인한다:

- 현재 브랜치가 `main`이 아니고, `gh pr list --head <현재 브랜치>`로 이미 열린 PR이 있거나 브랜치 이름/커밋 이력에 이슈 번호(`#123`, `123-...`, `issue-123` 등 이 저장소의 명명 관례)가 연결돼 있으면 '이슈에 엮인 브랜치'로 판단한다.
- 이슈에 엮인 브랜치면 새로 `docs/` 브랜치를 파지 않고, 스타일 교정 커밋을 그 브랜치 위에 그대로 얹어 같은 이슈/PR 흐름에 묶는다.
- 이슈에 엮이지 않은 브랜치(`main` 포함)일 때만 아래처럼 별도 `docs/` 브랜치를 새로 만든다.

승인 후:

1. 이슈에 엮인 브랜치면 이 단계를 건너뛰고 그 브랜치를 그대로 쓴다. 아니고 현재 브랜치가 `main`이면 새 브랜치를 만든다 — 문서 1개는 `docs/<가이드-슬러그>-style`, 여러 문서를 하나로 묶는 경우 `docs/style-pass-<YYYYMMDD>` 형태로 만든다.
2. 변경 파일만 `git add`로 스테이징하고, 커밋 메시지는 문서 1개면 `docs: <문서명> 컨벤션 정리`, 여러 문서면 `docs: <N>개 가이드 문서 컨벤션 정리` 형태로 작성한다.
3. 푸시한다 — 이슈에 엮인 기존 브랜치면 `git push`, 새로 만든 브랜치면 `git push -u origin <브랜치>`.
4. 이슈에 엮인 브랜치이고 그 브랜치로 이미 열린 PR이 있으면 새 PR을 만들지 않는다 — 푸시만으로 기존 PR에 커밋이 반영됐음을 사용자에게 알리고 끝낸다. 그 외의 경우에만 `gh pr create`로 PR을 만든다: 제목은 커밋 메시지와 동일하게, 본문에는 문서별로 어떤 체크리스트 항목을 교정했는지 bullet로 정리하고, 이슈에 엮인 브랜치였다면 관련 이슈 번호도 함께 적는다(`Closes #<이슈번호>` 등 저장소 관례가 있으면 그대로 따른다).
5. 완료 후 (새로 만들었거나 갱신된) PR URL을 사용자에게 전달한다.

## 하지 말 것

- 컨벤션 문서에 없는 새로운 스타일 규칙을 임의로 만들어 적용하지 않는다.
- 사용자 확인 없이 push/PR 생성을 진행하지 않는다.
- 톤 교정을 이유로 원문의 기술적 내용(코드, 수치, 링크 대상)을 바꾸지 않는다.
